# Финансовая модель

`Actor` владеет счетами; `Order` связывает покупателя и продавца;
`AccountTransaction` объединяет проводки `Entry`. Для демо у пользователя
один кошелёк в USD. Схема допускает кошельки в других валютах: уникальность
по `(actor_id, purpose, currency)`, сервисы выбирают кошелёк в валюте заказа.

Суммы — положительные целые `amount_minor` (`bigint`), без float.
USD 100.50 → 10050. Направление — `debit` или `credit`.
Баланс рассчитывается только по проведённым операциям:

- `asset`, `expense`: debit − credit;
- `liability`, `equity`, `revenue`: credit − debit.

Кошелёк — liability-счёт: обязательство платформы перед владельцем.
**Отрицательный баланс кошелька запрещён**, включая возвраты. Если продавец
потратил выручку и не может вернуть всю сумму, Cancel возвращает
`insufficient_funds`, исходный заказ остаётся `successful`, проводок нет.
Баланс ровно ноль допустим. На технические счета этот запрет не распространяется.

Complete: `created → successful`, одна операция `charge`, debit кошелька
покупателя и credit кошелька продавца на сумму заказа.
Cancel успешного заказа: отдельный `reversal` со ссылкой на charge; каждая
исходная Entry зеркалируется по направлению. Заказ становится `cancelled`.
Отмена `created` проводок не создаёт. Повторные Complete/Cancel идемпотентны.
Отменённый заказ провести нельзя. Частичного возврата нет.

Создание операции, всех Entry, posting и изменение статуса выполняются атомарно.
Сервисы блокируют Order, затем все затрагиваемые Account по возрастанию `id`.
Баланс проверяется после блокировки. Поддерживается `READ COMMITTED`.

PostgreSQL проверяет перед commit:

- операция проведена (`posted_at`), содержит минимум две Entry;
- debit = credit отдельно в каждой валюте;
- charge содержит ровно две Entry на сумму и в валюте заказа: debit кошелька покупателя и credit кошелька продавца;
- статус соответствует журналу: created без платежа, successful с charge без reversal, cancelled без платежа либо с charge и reversal;
- reversal полностью зеркалирует проведённый charge того же заказа;
- баланс каждого затронутого кошелька неотрицателен.

SQL-триггеры запрещают изменение/удаление Entry, удаление операций,
изменение проведённой операции и добавление к ней новых Entry. После posting
нельзя менять сумму, валюту, покупателя и продавца заказа — ни через модель,
ни прямым SQL; создание операции блокирует Order от конкурентного изменения. У счёта
с историей нельзя менять владельца, валюту, тип и purpose. Уникальные индексы
запрещают второй charge заказа и второй reversal исходной операции.
`opening_balance` не связан с заказом; charge/reversal требуют заказ.
Для opening_balance нет публичного endpoint или операции отмены.

Функции и триггеры сохраняются в `backend/db/structure.sql`.
Docker содержит PostgreSQL client 17 для dump/load. Гарантии относятся к обычным
записям в БД; администратор PostgreSQL может отключить триггеры. Конкурентные
тесты используют такую возможность только для удаления собственных записей
в тестовой БД, с `SET LOCAL session_replication_role = replica`.

## Сервисы

```ruby
result = Orders::Complete.call(order_id: order.id)
result = Orders::Cancel.call(order_id: order.id)

if result.success?
  result.order
  result.accounts
else
  result.error.code
  result.error.message
end
```

Ожидаемые ошибки: `not_found`, `invalid_transition`, `invalid_order`,
`account_not_found`, `insufficient_funds`. Неожиданные ошибки не маскируются.
Авторизация находится в HTTP-слое; внутренний вызов сервиса требует доверенного
вызывающего кода. `accounts` — модели, не зафиксированный снимок балансов.
При вызове во внешней DB-транзакции её commit остаётся ответственностью вызывающего.
