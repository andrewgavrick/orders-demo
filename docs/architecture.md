# Архитектура

## Модели

| Модель | Назначение |
| --- | --- |
| Actor | Участник: пользователь или система |
| Account | Счёт участника с валютой, типом и назначением |
| Order | Заказ между покупателем и продавцом, сумма, валюта и статус |
| AccountTransaction | Операция: charge, reversal или opening_balance |
| Entry | Проводка операции по счёту: направление и сумма |

У Actor есть счета, покупки и продажи. У заказа — платёж и, при возврате,
сторнирующая операция. AccountTransaction объединяет Entry; каждая Entry
ссылается на один Account. Начальное финансирование не связано с заказом.

В демо у пользователя один USD-кошелёк. Схема допускает другие валюты:
счёт уникален по (actor_id, purpose, currency). Заказ не хранит account_id:
сервисы выбирают кошельки покупателя и продавца по валюте заказа.

## Backend

Контроллеры V1 проверяют сессию, доступ к данным и форму запроса, затем
вызывают сервис. Общий ApiController формирует JSON и ожидаемые HTTP-ошибки.
В API-only приложении используется один префикс версии — /v1.

Orders::Complete и Orders::Cancel отвечают за переход состояния и финансовые
записи. Возвращают Result с заказом и счетами либо кодом и сообщением ошибки.
Неожиданные исключения пробрасываются и откатывают транзакцию.

Модели описывают связи и валидации. PostgreSQL обеспечивает ограничения,
которые должны действовать и при записи из консоли или прямым SQL:
неизменяемость истории, согласованность заказа и платежа, баланс проводок
и запрет минуса. Подробности — в [ledger.md](ledger.md).

Схема хранится в backend/db/structure.sql, поскольку обычный Ruby schema dump
не сохраняет SQL-функции и триггеры.

## Frontend

- App.tsx — выбор участника, восстановление и завершение сессии.
- OrdersDashboard.tsx — заказы, фильтры, баланс и форма создания заказа.
- JournalRows.tsx — операции и раскрытие проводок.
- api.ts — fetch, типы ответов и работа с денежными суммами.

Состояние хранится в React hooks. Отдельного менеджера состояния и роутера нет:
Orders и Transactions переключаются внутри dashboard. После оплаты или отмены
ответ API обновляет заказ и баланс, затем загружается журнал. Ошибка обновления
журнала не скрывает факт успешного сохранения операции.

Деньги передаются в minor units. Ввод преобразуется через BigInt без умножения
дробного Number. Интерфейс принимает денежные значения только в пределах
Number.MAX_SAFE_INTEGER; большие JSON-числа отклоняются. Суммирование и вывод
используют BigInt, чтобы не терять точность.

## Границы демо

Здесь нет банковского провайдера, реального пополнения, конвертации валют,
частичных возвратов и проверки личности. Cookie хранит выбранного участника;
выбрать можно любого пользователя демо. Авторизация после выбора действует
в HTTP-слое, а внутренние сервисы рассчитаны на доверенный вызывающий код.

Начальные деньги создаются только сидами: debit системного asset-счёта
и credit liability-кошелька. Это начальное обеспечение обязательств платформы.

Списки фронтенд загружает целиком через offset-пагинацию API. При добавлении
записей между запросами страниц возможны повторы; общего снимка списков и балансов
нет. Для небольшого демо используется ручной Refresh, без live-обновлений.

Docker Compose настроен для локальной разработки, а не production.
