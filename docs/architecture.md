# Архитектура

Rails API отвечает за заказы и двойную запись. React использует стабильный JSON-контракт
`/v1`. PostgreSQL хранит данные; пользовательских функций и триггеров в текущей схеме нет.

## Путь запроса

1. Контроллер проверяет сессию, принадлежность ресурса и strong parameters.
2. `Orders::CreateForm` проверяет исходные типы JSON до преобразования Active Record.
3. `Orders::Create`, `Orders::Complete` и `Orders::Cancel` выполняют сценарий и возвращают
   `Orders::Result`: заказ и счета либо ожидаемую ошибку.
4. `Ledger::Post` блокирует записи, вызывает `Ledger::Validation`, проводит журнал
   и меняет статус заказа в одной транзакции.
5. Jbuilder-шаблоны в `app/views/v1` формируют ответ. Kaminari выполняет пагинацию;
   concern `Pagination` проверяет допустимые параметры страниц.

Контроллеры не создают проводки и не проверяют финансовые правила.
Модели содержат связи, enum, небольшие scopes, валидации полей и защиту
изменения финансовой истории через обычный Active Record.
Сценарии работы с несколькими моделями находятся в `app/services`.
`BaseService` предоставляет единый `.call(...)`, сохраняя keyword-аргументы и блок.
Подключены только Active Model, Active Record, Action Controller и Action View;
неиспользуемые mailer/job/cable-заготовки удалены.

## Модели

| Модель | Назначение |
| --- | --- |
| Actor | Пользователь или системный участник |
| Account | Счёт с владельцем, валютой, типом и назначением |
| Order | Покупатель, продавец, сумма, валюта и статус |
| AccountTransaction | charge, reversal или opening_balance |
| Entry | Проводка по счёту с направлением и суммой |

Участник может покупать и продавать. У заказа может быть один charge и один
reversal исходного charge. Начальное финансирование не связано с заказом.
Баланс вычисляется из проведённых Entry; отдельного изменяемого поля balance нет.

`Order.visible_to` и `AccountTransaction.visible_to` задают выборки для участника.
Изменять заказ через API может только покупатель. Внутренние сервисы рассчитаны
на доверенный вызывающий код; они не выполняют аутентификацию.

## База и миграции

Текущая схема — `backend/db/schema.rb`. В базе остаются внешние ключи,
NOT NULL, CHECK для формы данных и уникальные индексы кошельков, оплат и возвратов.
Финансовые проверки и переходы состояний выполняются в Ruby.

Миграция `20260928000000_move_ledger_rules_to_services.rb` удаляет прежние функции
и триггеры без удаления данных. Исторические миграции сохранены для обновления
существующих установок. Новая база загружается сразу из актуального schema.rb.

Прямой SQL и методы обхода валидаций (`update_all`, `update_columns`) не являются
поддерживаемым способом финансовых изменений: они обходят сервисные гарантии.
Запись денег выполняется через сервисы; подробности — в [ledger.md](ledger.md).

## Демоданные

`db/seeds.rb` загружает `db/seeds/demo.rb`. Отдельный тестируемый класс создаёт
пользователей, счета и начальное финансирование через общий сервис проведения.
Повторный запуск не восстанавливает потраченные деньги. Запуск seeds предполагается
одним процессом; в production демофинансирование запрещено.

## Frontend

- App.tsx — выбор участника, восстановление и завершение сессии.
- OrdersDashboard.tsx — заказы, баланс и форма создания.
- JournalRows.tsx — журнал и раскрытие проводок.
- api.ts — fetch, типы ответов и точная обработка денежных сумм.

Состояние хранится в React hooks. После операции ответ API обновляет заказ и баланс,
затем загружается журнал. Ошибка загрузки журнала не скрывает успешную оплату.
Суммы передаются в minor units; ввод и форматирование используют BigInt.
Значения JSON за пределами Number.MAX_SAFE_INTEGER интерфейс отклоняет.

## Границы демо

Выбор участника не проверяет личность. Нет банковского провайдера, публичного
пополнения, конвертации валют и частичных возвратов. Возврат отклоняется, если
продавец уже потратил средства. Списки используют offset-пагинацию и ручной Refresh;
общего снимка нескольких запросов нет. Docker Compose предназначен для разработки.
